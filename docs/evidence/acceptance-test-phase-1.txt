=== connection test 2: Resend, 12:48:31Z — the defect ===

Pressed "Test connection" on the Resend card. The status flipped READY -> NOT FINISHED YET,
and the card contradicted itself:

  WEBHOOK READINESS   A correctly signed callback from this provider has been received
                      and understood
  NEXT STEP           We have your signing secret, but we have never actually received a
                      message signed with it, so we cannot yet say this connection works.

Both sentences are about the same fact, on the same card, at the same moment, and they
disagree. Screenshot preserved.

The database, read afterwards, read-only:

  provider  status    webhook_verified_at       last_check_at
  hubspot   ready     NULL                      2026-09-22T12:47:08.587Z
  resend    testing   2026-09-21T07:32:50.109Z  2026-09-22T12:48:31.662Z

So the callback did arrive, on 21 September. The webhook readiness line is the true one. The
status and the next step are wrong, and the status is wrong *in the stored row*: pressing a
button that only asks how a connection is doing moved that connection backwards.


=== why ===

`customerPort.testConnection` called `revalidateConnection` with a connection object of only

  { provider, account_id, reverify_account }

omitting `webhook_verified_at`. That is the single field `resend.ts` decides readiness on:

  const webhookProven = typeof input.connection.webhook_verified_at === 'string' && ...
  return { ok: hasSecret && webhookProven, ... }

Undefined, so never proven, so `ok: false`, so `RESEND_AWAIT_CALLBACK_STEP` — which is the
sentence quoted above — and `revalidateConnection` maps not-ready to `testing`, which
`connections.setStatus` then wrote.

Meanwhile the page's own webhook line came from a *separate* query of the same column, a few
lines further down the same method, which read the true value. One fact, two sources, one of
them starved of its input: that is the contradiction, exactly.

Two things make this worse than a wrong label.

**It had already been found once.** The credential-save path in the same file carries the
value in deliberately, with a comment saying so: "A webhook that has already been proven stays
proven. Without carrying this in, a customer who re-pastes their API key would silently drop a
`ready` Resend connection back to `testing`." The identical omission in `testConnection` was
never noticed, because `testConnection` had no test of any kind — not one case anywhere in the
tree touched it.

**It was a dead end, not a blip.** `markWebhookVerified` is the only route from `testing` to
`ready` for a webhook-dependent connection, and the route that calls it fires only while
`webhook_verified_at IS NULL` (`routes/webhooks/resend.ts:340`). Our row is not null. So no
later delivery, however correctly signed, could have climbed the connection back out. The only
customer-reachable escape was re-pasting the API key, because that path does carry the value.

Severity: high. Wrong, persisted, customer-visible, self-contradicting, and unrecoverable by
the obvious action.


=== what phase 1 did not establish ===

Stopped here deliberately, so most of the matrix is untested and is recorded as untested
rather than passed:

  correct CRM correlation and recipient        not reached
  wrong recipient                              not reached
  existing record, wrong correlation           not reached

Two limits found while reading, which no amount of running would have changed:

**300 runs cannot be reached through the customer flow.** The guided test verification is rate
limited to four per hour per workspace (`consume(db, 'test-verification:<ws>', 4, 3600)`).
Three hundred runs is seventy-five hours of continuous pressing. So the 300-run volume is
untested, and the 500-run allowance boundary is untested with it. Raising either would mean
altering production entitlement data or the limiter, which is exactly what was ruled out.

**The external automation path is untested.** The website's guided path exercises the internal
pipeline. It does not prove an outside automation signs and sends events correctly. No
authorised automation was available to trigger, so that path is marked explicitly untested
rather than inferred from the guided one.

Allowance consumed by phase 1: none. Connection tests do not consume verification allowance,
and no verification was started. The reconciliation at the end of a resumed run therefore
starts from the same 0/500 recorded above.

=== why, and why it is worse than a wrong label ===

`statusForError` maps PROVIDER_UNAVAILABLE, RATE_LIMITED, NOT_FOUND, AMBIGUOUS_MATCH and
INVALID_EVIDENCE to `not_connected` by falling through a switch. That is defensible for a
first-time connect. For a re-check of an established connection it says "you have never
connected this provider" on the strength of the provider having a bad minute.

`testConnection`'s own doc comment claimed this path answered `degraded`, and said exactly
why that mattered: "making them re-paste a working key because HubSpot had a bad minute would
be the product punishing them for somebody else's outage." Only the *thrown* path answered
`degraded`. And the thrown path is effectively unreachable: the connector catches timeouts and
returns them as classified errors, so every realistic outage takes the classified branch. The
documented intent was never the deployed behaviour.

The blast radius is not the label. The scheduler's `USABLE_STATUSES` is `{ready, degraded}`.
`not_connected` is outside it, so a transient provider error takes the connection out of
service for real verification runs — every run needing its evidence would come back unverified
— until a human presses the button again at a luckier moment. Severity: high.

Fixed: an uninformative failure (PROVIDER_UNAVAILABLE, RATE_LIMITED) now returns the status the
connection already had, so a check that learned nothing changes nothing. CONN-905 and CONN-906
hold it, mutation-checked at `expected 'not_connected' to be 'ready'` — the production symptom.
CONN-907 holds the over-correction: an expired token is measured, not merely unreachable, and
still moves the status. CONN-188 was corrected: it was named "changes nothing when the provider
is merely unreachable" while asserting `status not.toBe('ready')`, which is the opposite of its
own name and the reading under which an outage may rewrite health nobody measured.

Note for the resumed run: Resend answering an error at 13:04:54Z is itself unexplained. It may
be a genuine transient, or it may be Resend refusing us after four checks in twenty minutes.
The acceptance test cannot tell from the customer surface, and the next phase should re-test
once, cold, before reading anything into it.


=== a correction to this record ===

Both entries above, and the commit messages for both fixes, said `testConnection` had no test
coverage at all — "not one case in the tree touched it". That is wrong, and the mistake was
mine: I searched the test tree for the method name, and the cases exercise it through the
route rather than by calling it, so the search found nothing and I believed it.

`tests/integration/customer/connection-test.test.ts` holds eight cases against the real route
with a stubbed provider: CONN-518 through CONN-523, CONN-526 and AUTH-518.

The accurate account is narrower and more useful than "untested":

**Defect 1 (Resend webhook) was untested.** Not one of those eight cases mentions Resend. They
are all HubSpot, which is polled and has no `webhook_verified_at`, so the field defect 1 lived
in could not arise in any of them.

**Defect 2 (outage demotion) was half-tested, and the missing half was the defect.** CONN-521
is named "a provider that cannot be reached leaves the stored credential alone and says so",
and it asserts the customer-facing sentence, the credential count and the error code. It never
asserted the connection's status. Two other cases in the same file do assert status — CONN-519
that a good check reads `ready`, CONN-522 that a refused credential does not — so status was
plainly considered; it was simply not checked on the outage path, which is the one path where
changing it is indefensible.

That is the same shape as CONN-188 in the unit suite: a case whose name states the whole
requirement and whose assertions cover part of it. Two independent tests, both named for
"changes nothing", neither checking the thing that changed.

CONN-521 now asserts the status is still `ready` after an outage. It was strengthened rather
than replaced, and it fails without the fix.

=== the third defect: a failure that reports the wrong kind of failure ===

Both runs settled FAILED. The verdict *bucket* is correct and deliberate: `decideRunStatus`
treats an authoritative absence, after the deadline, with healthy evidence access, as a real
failure — `isAuthoritativeAbsence` is described in that code as "the only route from unknown
to failed". The enquiry genuinely did not produce the record. FAILED is right.

The explanation is false. The run page read:

  STATUS   FAILED
           We retrieved the evidence and it contradicts at least one of your required checks.
           At least one required check is contradicted by the evidence we retrieved.

directly above its own table of checks:

  COULD NOT CONFIRM   The CRM record carries this enquiry reference
                      no reading / no evidence / We did not retrieve a value
                      reason RECORD_NOT_FOUND
  COULD NOT CONFIRM   A CRM record was created
                      no reading / no evidence / We did not retrieve a value
                      reason RECORD_NOT_FOUND

and a counter reading:

  0 of 2 items did not match what was reported.

Three statements on one page: nothing was retrieved, nothing mismatched, and "we retrieved the
evidence and it contradicts your checks".

**Why.** `decideRunStatus` computes two distinct reasons, `FAILED_CONTRADICTED` and
`FAILED_ABSENT` — the latter reading "The deadline passed and the connected systems confirmed
the expected record or message does not exist", which is exactly right for these runs. That
reason is never stored: `runs` has no `reason` column (columns confirmed by pragma). It
travels into the scheduler's return value for logging and stops there. Every customer surface
therefore re-derives a sentence from the status alone — `summarise()` in `customerPort`,
`RUN_TEXT.FAILED` in `explain.ts`, and `comparatorSentence` in the UI — and all three assume
FAILED means contradicted.

So this is not an edge case. **Every absence-failure this product has ever reported has told
the customer their evidence contradicted their checks.** The two send a customer to different
places: one to hunt a data mismatch, the other to find out why nothing was created.

Severity: high on correctness of a customer-visible verdict explanation, below the first two
on consequence, because the verdict bucket is right and the table beneath it tells the truth.

**Fixed** by deriving the sentence from the assertion rows the page already renders, rather
than adding a column — which makes the headline and the table structurally unable to disagree,
since both now read the same rows. VERIFY-901 holds the sentence, VERIFY-902 the
over-correction (a real contradiction still says so), VERIFY-903 that `explainRun` passes the
results through, VERIFY-904 that calling it with no results keeps the old answer rather than
guessing. CUST-961 and CUST-962 hold the counter, which had no test at all.

Runs spent in phase 3: 2 of 500. Two of this hour's four guided verifications used.


=== what remains untested, and why ===

**The success path has never been demonstrated anywhere.** Both staging runs settled UNVERIFIED
with CONNECTION_UNAVAILABLE; production has now produced two FAILED. No deployment of this
product has ever produced a VERIFIED result. Proving it needs a real HubSpot contact carrying a
known `itisyou_verify_ref`, and a real Resend message id with a known recipient — fixtures only
the account owner can create. Requested; not yet available.

Blocked on the same fixtures, and therefore untested:
  correct CRM correlation and recipient      needs a real record and message
  wrong recipient                            needs a real message to mis-address
  existing CRM record, wrong correlation     needs a real record

**300 runs and the 500 boundary remain unreachable.** Four guided verifications per hour per
workspace is 75 hours for 300. Untested, and not reachable without altering production
entitlement data or the limiter.

**The external automation path remains untested.** No authorised automation was available to
trigger, and the guided form explicitly proves nothing about it: the page says so itself.

=== customer friction observed, by impact ===

1. **A test run is indistinguishable from a real one in the runs list.** It is labelled on its
   own page ("You started this one") and correctly excluded from the verification rate, but
   `/app/runs` shows no badge and offers no real-versus-test filter. Two test runs currently
   read as two customer failures to anyone scanning the list. Highest impact of the items
   here, because it misrepresents the workspace's record at a glance.

2. **The allowance panel never shows `reserved`.** The data exists. A customer cannot see how
   much of their allowance is committed to runs still in flight.

3. **No oldest-pending age.** "3 pending" reads the same at three minutes and three hours.

4. **Duplicate submissions are silent.** No confirmation, no warning, and a second identical
   enquiry costs a second run.

5. **Invalid input is refused by the browser's native bubble**, which is the one error in the
   product that does not look like the product.

6. **The verdict sentence now appears twice on a settled run page.** Introduced today.
