## 2. Blockers, in the order they must fall

1. **Owner enrols the authenticator** on `https://verify.itisyou.app/admin/authenticator` and confirms a code (O13). Until then nothing consequential can be done in the panel.
2. **Owner creates the isolated test workspace** (`/owner/customers`, outlook address, "Test workspace" ticked) and signs in as it (O14, O6).
3. **P1/P2: production-origin sandbox checkout** driven in the owner's browser with a Stripe test card, then activation, exactly-once allowance, replay refusal, `/app/billing` and `/app/usage` read back on production. Still in **test mode** — this is the last proof before any live configuration.
4. **L5: owner supplies the seven legal-identity values** (or states which do not apply, e.g. no VAT number, sole trader). One commit in `legal.ts`, one deploy.
5. **L6: owner decides the VAT position.** Recommended for a UK sole trader below the threshold: "£29.00 includes any VAT that applies; we are not VAT-registered" and remove the "calculated by our payment provider" sentence. If VAT-registered or using Stripe Tax: add a tax registration in the parent account and `automatic_tax: { enabled: true }` at checkout. Either way one commit, one deploy.
6. **L7: add the two owner alerts** (`spending_decision` on the first live `checkout.session.completed`; `critical_incident` on every live `invoice.payment_failed`), tested through the real webhook path. One commit, one deploy.
7. **L2/L3: live objects in the parent account** — §4 steps 1–5.
8. **L4 and go-live** — §4 steps 6–9.
