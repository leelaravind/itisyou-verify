SPEC-02 / VERIFICATION_METHODOLOGY / INDEPENDENT_READBACK
OBSERVER ENGINE: v4.18.2-prod (london-dc1)
science EMPIRICAL TELEMETRY MODEL

An automation platform reporting success is only reporting on its own work.

When Make, Zapier, n8n, or an internal Python runner finishes with an HTTP 200, it only confirms the runner process did not crash while dispatching its outbound socket write. It does not prove the destination CRM wrote the row, the mail exchange accepted the message, or the database committed the transaction. We wait for an agreed settling window, query the destination APIs independently with read-only tokens, and record what actually landed.

Our Outage Is Not Your Failure

The inspection adapter in eu-west-2 timed out attempting to reach destination API endpoints (Connection reset by peer). Because ITISYOU Verify could not independently inspect the target system, this check is marked [◐ UNVERIFIED].

We will never mark an automation as FAILED because of our own network or adapter downtime, nor will we guess that it succeeded. An uninspected state is always recorded with empirical skepticism.

TAXONOMY REFERENCE

The Strict Four Statuses Rule

In forensic inspection, color is never used as the sole conveyor of information. Each state is strictly defined by an unambiguous glyph and immutable text string.

✓ VERIFIED

Target API responded with matching entity payload during or after the settling delay. Fields confirmed written in target ledger.

✕ FAILED

Destination target responded with 404 Not Found or zero records after the settling window expired. Work did not land.

◐ UNVERIFIED

We could not check. Downstream endpoint returned rate-limits (429), gateway timeouts (504), or network resets. First-class outcome.

⏱ PENDING

Settling timer currently counting down. Query dispatch is intentionally paused to allow async backend pipelines to finalize.

visibility_off

What this cannot detect

If a workflow never starts, and the workflow is the thing that tells us a run was expected, we will not know a run was missing.

Readback verification works by observing an ingress trigger or scheduled expectation, waiting out the settling window, and querying destination APIs. If your incoming webhook is dropped before it reaches your runner, or if a schedule trigger fails silently at the platform provider before notifying our webhook listener, our ledger has no record that an event was supposed to occur.

To detect silent workflow non-starts, you must configure external synthetic heartbeats or dead-man switches at the primary event source itself. We verify what was attempted; we cannot invent awareness of events that never announced their existence.

info RECOMMENDED PATTERN: Pair ITISYOU Verify with external cron heartbeats at primary webhook intake gateways.
